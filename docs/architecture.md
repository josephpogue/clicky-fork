# Clicky Fork: architecture

## Overview

Clicky Fork is a macOS menu-bar assistant (no dock icon, no main window). The user starts a session from the menu bar. During a session the app listens on the microphone and transcribes speech on the Mac, saves screenshots of every display when the app or window changes or the screen changes clearly, and logs it all to a session folder. A press of the question key (a lone tap of right Command unless the user chose another key in Settings) starts a spoken question; the next press sends it. The question goes, with the current screens, a short note of what happened since the last question and (when the question is about an earlier moment) that moment's screenshot, and (when search folders are set) the passages from the user's notes that match the question, to Claude through the official `claude` CLI or to ChatGPT through the official `codex` CLI, each on the user's own subscription login kept in the app's own config folder. Claude may also search and read those notes inside the same request. The answer streams in as it is written and shows as text beside the cursor, is read aloud with a built-in macOS voice, or both (Settings, Answer by), and a pointer flies to the spot its `[POINT:...]` tag names. Moving the mouse keeps the text; any click or keypress fades it. No window opens during a session by itself; the chat window holding the whole conversation opens only from the menu-bar panel's Open chat row or, during a session, the chat key (right Command + comma unless the user chose another in Settings), which also closes it. Stop turns everything off, cleans up near-duplicate screenshots, writes `log.md`, and (when on) asks for one text-only summary. Save files a session into the user's notes folder under a project.


## Architecture

- **App type:** menu bar only (`LSUIElement=true`), SwiftUI with AppKit bridging (`NSStatusItem`, `NSPanel`, `NSHostingView`), `@MainActor` UI state, async/await.
- **Session:** `SessionCoordinator` (app) starts and stops the pieces through the phases in `SessionLifecycle` (idle, starting, running, stopping). Screen, microphone and key tap start together only once speech, the permissions and the provider are ready; quit in any phase but idle waits for a clean stop. A Start cancelled or quit before the session shows as running removes its session folder, even when capture had begun (`SessionStartEnding`); a Start that fails after capture began keeps a short session and shows the notice. The chat window, when open, shows the same phase as the panel. `SessionQuestionFlow` (ClickyCore actor) runs each question: transcribe, capture, pick an earlier moment, build the turn, ask, parse the point, log, and start a fresh conversation with a text recap after 15 turns or 40 images.
- **Providers:** both behind `AnswerProvider` / `ProviderAccount`. Claude: one long-lived `claude -p --input-format stream-json --output-format stream-json` process per session with no built-in tools and no settings (`--tools ""`, `--setting-sources ""`, `--strict-mcp-config`) and every answer streamed (`--include-partial-messages`); `--safe-mode` while the brain is off, and with search folders set the brain helper through an inline `--mcp-config` and `--allowedTools` for its two tools only (`--safe-mode` blocks MCP servers, so it is dropped then); `CLAUDE_CONFIG_DIR` = the app's `providers/claude-config`; model changes use the CLI's in-place `set_model`, dig deeper's effort uses `apply_flag_settings`, and a new question ends a running answer with the `interrupt` control request. ChatGPT: `codex exec` then `codex exec resume <thread>` per question, `CODEX_HOME` = the app's `providers/codex-home`, low reasoning effort, the thread deleted at Stop. Both refuse an API-key login. Codex runs with every model tool turned off (`CodexToolRestrictions`) and gets only the passages the Mac found; a new question ends its running `codex exec`. Neither `startConversation` sends anything: a recap rides on the next question.
- **Brain search:** with search folders set in Settings (`settings.brainSearchFolderPaths`; empty means off and the app behaves as before), `BrainIndexService` (app) keeps a SQLite FTS5 index of their markdown and text files at `<data>/brain-index/index.sqlite`, refreshed at launch, on a folder change and at Start. `BrainFileRules` decides what is never indexed or read (secrets, `.git`, `node_modules`, worktrees, `-prod` checkouts, build output). Each question attaches the passages above the score floor (`BrainIndex.passages`, boosted toward the project the front window names). Claude may also call `search_brain` and `read_brain_file`, served over MCP stdio by the bundled helper `Contents/MacOS/ClickyBrainTools` (`BrainToolServerCore`), which reads only files that resolve inside a search folder (`BrainFileReader`). The answer streams: `StreamingAnswerText` hides half-written tags, `CheckingNotesRule` decides when the app shows and says "Checking your notes", `SpokenSentenceSplitter` speaks it sentence by sentence, and `GrowingAnswerBubbleState` and `GrowingAnswerChatState` grow the bubble and the chat message. A question starting "dig deeper" (`DigDeeperMatcher`) runs on the Settings dig-deeper model and effort.
- **Speech:** `SessionSpeechPipeline` reads the microphone only between Start and Stop, splits utterances with an energy segmenter, and transcribes them with Parakeet TDT 0.6b v3 on the Mac. Its timeline is anchored to when audio arrives (re-anchored after a gap), and Stop drains the last words. The model loads at app launch (about 45 s the first time on a Mac, under a second after); a download that fails for 300 s falls back to Apple Speech.
- **Screen capture:** ScreenCaptureKit, all displays, the app's own windows excluded, 1280 px long side, JPEG about 75 KB. Saves on session start, each question, app or window switches and clear screen changes (32x20 grayscale thumbnail difference), at most one save every 2 s. Screens are numbered by display order. No text is ever read off a screenshot.
- **Answers beside the cursor:** `CursorAnswerPresenter` shows the answer, a notice or the speaker capsule in `CursorAttachedPanel`, a borderless panel that ignores the mouse and never becomes key, so the user's app keeps every click, key and scroll. It follows the cursor each frame, flips left or up near an edge, and rides under the pointer's label while the pointer is out (`CursorBubbleLayout` holds the placement, width and line-cap rules). A global click or key monitor fades it. `SpokenAnswerPlayer` reads answers with `AVSpeechSynthesizer` and the voice from Settings (`SpokenVoiceChoice`); a new question stops it.
- **Pointing:** answers end with `[POINT:x,y:label:screenN]` in that screenshot's pixels; `PointMapper` maps it to the display and the overlay flies the pointer there along upstream's bezier arc.

## Key Architecture Decisions

**Menu bar panel:** `NSStatusItem` plus a custom borderless non-activating `NSPanel`, dismissed by a global click-outside monitor. The icon shows a red dot while a session runs.

**Chat window:** a floating non-activating `NSPanel` whose `canBecomeKey` is false, so showing, hiding or updating it never takes keyboard focus from the user's app. It opens only from the panel's Open chat row or the chat key (`AppWindowRouter.toggleChat`), never by itself. Each answer is one message: `AnswerPartsTracker` (ClickyCore `Questions/AnswerParts.swift`) splits the answer into parts (a new part at each tool call and each "Correction:" sentence; within a part, the model's `[CHAT]` marker ends the cursor text) and joins every part's cursor and chat text as paragraphs; log, recap and session browsing strip the marker with `AnswerChatMarker.removing`. Fixed-size hosting views set `sizingOptions = []` or they can render blank.

**Cursor answer panel:** `ignoresMouseEvents = true` and `canBecomeKey` false, so the answer beside the cursor can never take input from the user's app. It never cuts text: `CursorLineState` (ClickyCore) shows the newest part's longest leading run of whole cursor sentences that `AnswerBubbleMetrics.fitsInBubble` says fit under `CursorBubbleLayout.maximumBodyHeight`, with a "More in chat: <chat key>" footer when the chat holds more, and hands the voice exactly those sentences, once each; there is no scrolling inside it. A new part's first line always reaches the bubble, the "Checking your notes" line goes as soon as the next line shows or the answer ends in any way (`GrowingAnswerBubbleState.answerFinished`), and the footer is redrawn when the chat key it names stops working or changes (`CursorFooter`). `SentenceRule` (ClickyCore) is the one sentence-end rule for the bubble and the voice: abbreviations, initials (a single capital ends a sentence only before a common opener word, and never as a list label such as "A." at the start of a clause), ellipses (only a non-pronoun, non-article opener settles one), closing quotes and brackets, and text before a hidden tag or marker counts as finished.

**Question key:** a `CGEvent` tap installed only during a session. The key is a `QuestionKeySpec` saved in `AppSettings` (default right Command, so existing users see no change): one modifier with its side (counts only when pressed and released within 1 s with no other key, modifier or mouse button in between), modifiers only (the exact set, either side, held clean for under 1 s), or modifiers plus one regular key (fires on the key going down and removes that key press, and its release, so it does not type into the user's app). The tap is listen-only except for a combination with a regular key, which needs an active tap; applying a new key swaps the tap when that changes. A bare regular key is refused. Settings records a new key with a local `NSEvent` monitor and the old key is suspended while it records. The chat key shares the same tap (`TwoKeyDetector`; both detectors see every event before anything is removed, so right Command + comma also spoils a lone right-Command tap). It is a `.sidedCombination` (`QuestionKeySpec`, sides kept, default right Command + comma, saved as `settings.chatKey`), so left Command + comma passes through; its press, repeats and release are removed. `KeyOverlap` refuses a question or chat key that a press could share with the other, and a saved chat key that overlaps (or is not sided) is inactive: Settings says so and the footer points at Open chat instead. The tap runs on its own thread (`QuestionKeyTapWorker` in `QuestionKeyMonitor.swift`); key changes and suspension are queued to that thread, and signals and chat-key presses hop to the main actor. Only one Settings section records at a time (`KeyRecordingTracker`); `KeyRecordingSession` holds a section's recording and refusal state, and a refusal clears on Record, a good Reset, the clash going away, Cancel, Escape and Settings closing. An already-off chat key never blocks a new question key. `TwoKeyDetector` keeps hiding a key-up it promised to hide through suspension and key changes. `KeyTapHealth` retries a failed or switched-off tap once and checks Accessibility every 3 s and when a Settings recording starts (`AXIsProcessTrusted()` keeps saying true and the old tap keeps running after Accessibility is taken away, so the live check is whether a new removing tap can be made: if not, the old tap is removed and the loss reported); a loss (`QuestionKeyMonitor.onTapLost`, decided by `KeyTapLossState`) never cuts an answer: the chat and the menu-bar panel get `KeyTapNotice.lost` at once, the cursor once the answer has ended and its reading has finished by any path (`SpeechTurnTracker.takeEndedReading`; a provider-failure or usage-limit notice that takes the cursor first drops the waiting cursor notice, the panel, chat and Settings still carry it), Settings shows a lost line under both keys, the footer stops naming the chat key, and a question being listened for is dropped (`SessionQuestionFlow.abandonListening`); Stop or the next Start clears it all.

**One provider interface:** the session, recap and log code never knows which provider answers; a usage-limit failure on Claude shows a notice beside the cursor and a one-tap switch to ChatGPT in the menu-bar panel that carries the conversation over as a text recap.
